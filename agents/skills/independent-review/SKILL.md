# 독립 에이전트 리뷰

메인 세션이 놓친 오류·누락·위험을 찾기 위해, 작성 과정을 모르는 에이전트에게 결과물을 처음부터 검증하게 한다.

## 1. 대상 정하기

인자나 요청 문맥에서 대상과 유형을 정한다. 지시가 없으면 이 세션에서 마지막으로 만들거나 고친 결과물을 대상으로 한다. 후보가 여럿이면 사용자에게 묻는다.

| 유형 | 대상 지정 방법 |
| --- | --- |
| 플랜 | plan.md 경로, 작성자 산출물(선례 분석 등) 경로 |
| 코드 변경 | worktree 경로, 레포, 브랜치, 리뷰 범위 명령(`git diff origin/<base>...HEAD`, `git log --oneline --no-merges origin/<base>..HEAD`) |
| SQL | SQL 파일 경로, 실행 DB·스키마, 바인드 변수 |
| 문서 | 문서 경로 또는 URL |

사용자가 특정 관점("난이도가 적절한지", "이슈 요건과 맞는지")을 말했으면 그 관점을 확인 포인트 맨 앞에 둔다.

## 2. 프롬프트 작성 규칙

- `Agent` 도구, `subagent_type: "Plan"`, `run_in_background: false`로 파견한다.
  - `Plan`은 Edit·Write가 도구 수준에서 빠져 있어 읽기 전용이 프롬프트에만 의존하지 않는다(Bash는 남으므로 아래 절대 규칙도 함께 준다).
  - 다음 단계(3. 결과 처리)가 리뷰 결과에 달려 있으므로 포그라운드로 기다린다.
  - **`fork`는 쓰지 않는다**(메인 컨텍스트를 물려받아 독립성이 사라진다).
- 에이전트는 이 대화를 모른다. 필요한 사실은 모두 프롬프트에 적는다. 경로는 절대경로로 쓴다.
- **사실과 의도만 전달하고, 메인 세션의 판단·결론은 넣지 않는다.** 작성자 산출물은 "근거가 아니라 검증 대상"이라고 명시한다.
- 요건은 요약과 함께 **원문 조회 방법**을 준다(이슈 트래커·문서를 조회하는 CLI 명령, MCP 도구, URL 등 이 세션에서 쓸 수 있는 것). 에이전트가 원문으로 요약을 검증할 수 있어야 한다.
- 재리뷰이면 1차 이후 반영한 커밋·변경 목록을 "검증 대상"으로 주고, 1차에서 정리된 항목은 해결 여부만 한 줄로 적게 한다.

### 프롬프트 골격

```
당신은 이 작업에 참여하지 않은 독립 리뷰어입니다. {대상}을 처음 보는 시니어 개발자 입장에서 비판적으로 검토해 주세요.
작성자의 판단에 기대지 말고 코드·원천 문서로 직접 확인해 오류, 누락, 위험을 찾는 것이 목적입니다. 보고는 한국어로 작성합니다.

## 절대 규칙
- 읽기 전용입니다. 파일 수정·생성, 커밋·push, git 상태 변경, 이슈 트래커·위키 쓰기를 하지 마세요.
- 빌드·테스트를 실행하지 마세요.
- DB 업무 데이터(SELECT·COUNT)를 조회하지 마세요. 스키마·인덱스·코드 테이블 같은 메타 정보 조회는 허용합니다. 데이터 확인이 필요하면 "확인 필요"로 적으세요.
- 실행 계획은 ANALYZE 없는 `EXPLAIN`으로만 확인하세요. `EXPLAIN ANALYZE`처럼 문을 실제로 실행하는 방식은 금지합니다(UPDATE·DELETE면 데이터가 바뀝니다).
- 비밀값(계정·비밀번호·토큰)을 출력하지 말고, `.env*`·`.mcp.json`·`~/.claude.json`을 읽지 마세요.

## 리뷰 대상
{경로, 범위 명령, 실행 환경}
- {작성자 산출물}: 작성자 결과물이므로 사실 근거가 아니라 검증 대상으로 보세요.

## 의도·요건
{이슈 의도, 확정된 정의, 전제, 범위 밖 항목(다른 팀 담당 등)}
- 원문: {조회 명령·도구·URL}

## 맥락·자료
{프로젝트 CLAUDE.md·AGENTS.md, 레포 경로(읽기 전용), 스택·버전, 인코딩 주의, 사용할 CLI·MCP}

## 확인 포인트
{사용자가 지정한 관점 + 아래 유형별 기본 관점에서 이 대상에 맞는 것}

## 보고 형식
- 결론 한 줄
- 발견 사항을 심각도(높음/중간/낮음) 순으로, 최대 15개. 각 항목: 위치(파일:줄 / 장·항목 / CTE명), 문제, 근거(코드 인용·커밋·SQL), 실패 시나리오, 수정 제안
- 확인했지만 문제없던 항목은 한 줄씩
- 검증하지 못한 가정 목록
- 코드·문서로 확인한 사실과 추측을 구분하고, 사소한 문구 지적은 하지 마세요.
```

### 유형별 기본 확인 포인트

- **플랜**: 사실과 다르거나 근거가 약한 주장, 내부 모순 / 구현·운영·배포·보안 누락 / 규모에 비해 과한 설계 / 운영 DB 부하·롤백 위험 / 단계 의존 관계와 커밋 단위 / 담당 범위(다른 팀 영역 포함 여부)
- **코드 변경**: 의도와 실제 동작 일치, 제거·변경한 심볼의 잔여 참조(템플릿·스크립트·설정·테스트 포함 레포 전체) / 환경(local·dev·stg·prod 등)별 동작 차이 / 테스트가 의미 있는 검증을 잃지 않았는지 / 언어·프레임워크 버전 호환 / 머지 충돌 해결의 적절성 / 배포 후 장애·롤백 고려
- **SQL**: 요건(대상·기간 경계·집계 정의·금액 부호) 일치와 해석이 갈리는 지점 / 이중 집계·누락(1:N 조인, 취소·부분 취소) / 코드값 목록 누락·오포함 / 인덱스 사용과 실행 부하(테이블 메타·ANALYZE 없는 `EXPLAIN` 실행 계획 확인) / UPDATE·DELETE면 대상 범위와 되돌리기 방법
- **문서**: 원천(코드·기획서·이슈)과 어긋나는 서술 / 빠진 항목 / 독자가 오해할 표현

## 3. 결과 처리

1. 리뷰가 끝나면 지적 사항마다 메인 세션이 직접 코드·문서로 확인해 판단을 붙인다.
   - **동의**: 맞는 지적. 반영 방법을 한 줄로 적는다.
   - **반박**: 리뷰어가 맥락을 몰랐거나 틀린 지적. 근거(파일:줄, 사용자 결정 등)를 적는다.
   - **확인 필요**: 메인도 판단할 수 없는 것. 사용자에게 무엇을 확인할지 적는다.
2. 사용자에게 보고한다. 리뷰어 원문 지적의 요지, 심각도, 메인 판단을 표로 정리하고 "문제없던 항목"은 한 줄로 요약한다.
3. **사용자 승인 없이 반영하지 않는다.** 사용자가 "반영"을 지시하면 동의 항목부터 반영한다.
4. 사용자가 재리뷰를 요청하면 같은 에이전트를 재개하지 않고 새로 파견한다(1차 결론에 끌려가지 않게). 이때 2장의 재리뷰 규칙을 따른다.
