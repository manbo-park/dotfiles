# PR description 생성

## 1. 자료 수집

| 자료 | 수집 방법 | 용도 |
|------|-----------|------|
| 티켓 ID | `git branch --show-current`에서 `<대문자>-<숫자>`(외부 이슈 트래커) 또는 이슈 번호(GitHub Issues) 추출. 없으면 아래 티켓 없는 경우 규칙을 따른다 | 개요·참고 |
| 티켓 내용 | GitHub Issues면 `gh issue view {번호}`, 외부 이슈 트래커면 사용 가능한 CLI·MCP로 조회. 없으면 사용자에게 붙여넣기를 요청한다 | 개요(배경·증상) |
| 커밋 목록 | `git log --reverse --format='%h %s' --name-only {target}..HEAD` | 변경 요약(커밋별 수정 파일 포함) |
| 변경 코드 | `git diff {target}...HEAD` (필요 파일만 읽는다) | 변경 상세·영향 범위·검증 |

- target 브랜치는 사용자가 지정하지 않으면 `dev` → `develop` → `main` → `master` 순으로 존재하는 것을 쓴다.
- PR 번호나 원격 브랜치명만 주어지고 로컬 체크아웃이 없으면 `gh pr view {번호} --json baseRefName,commits,files`와 `gh pr diff {번호}`로 target 브랜치, 커밋, diff를 가져온다.
- 티켓 조회에 실패하면 티켓 설명 붙여넣기를 요청한다. 배경을 추측해서 채우지 않는다.
- 브랜치명에 티켓이 없으면 `gh issue list`에서 관련 이슈를 찾는다. 찾지 못하면 묻지 않고 티켓 없이 진행한다. 단, `git log {target} --format=%s -20`의 커밋 제목에 티켓 ID가 쓰이는 저장소면 외부 이슈 트래커를 쓰는 것이므로 사용자에게 묻는다.
- 티켓 없이 진행할 때 개요의 배경은 커밋 본문과 diff에서 확인된 목적만 쓴다.

## 2. 작성 규칙

- 사람이 읽는 문서다. 리뷰어가 알아야 할 것만 쓰고, 쉬운 말로 짧게 쓴다. 정보가 많아 보이는 것보다 빨리 읽히는 것을 우선한다.
- 어투: 개요와 변경 상세는 "~입니다", "~합니다" 존댓말. 나머지 문단(변경 요약·영향 범위·검증·참고)은 표·항목 위주라 명사형 종결("~수정", "~확인")로 쓴다.
- AI 문체를 피한다. 줄표(—), 가운뎃점(·), 볼드 강조를 남용하지 않는다. 볼드는 문단 전체에서 꼭 필요한 한두 곳 이하로, 나열은 쉼표나 항목으로 푼다.
- 작업 도중 바뀐 결정, 시도했다가 버린 방식, 논의 경위는 쓰지 않는다. 예외는 그 결정을 모르면 코드를 이해할 수 없는 경우뿐이며, 그때는 변경 상세에 한 줄로 넣는다.
- diff와 티켓에서 확인된 사실만 쓴다. 확인되지 않은 영향 범위·검증 방법은 `(확인 필요)`로 표시하고 사용자에게 묻는다.
- AI 생성 표식(`Generated with Claude`, `Co-Authored-By` 등)을 넣지 않는다.
- 문단 제목은 `## ` 헤더로 고정하며 순서를 바꾸지 않는다.

## 3. 문단별 지침

### 개요
첫 줄은 이번 PR 전체 변경 사항을 한 문장으로 요약한다. 문서에서 가장 중요한 줄이며, 이 줄만 읽어도 무엇을 했는지 알 수 있어야 한다.
"어느 화면(영역)의 무엇을 어떻게 했습니다" 형태로 쓴다.
예) 설정 페이지 프로필 편집 모달에서 저장 후 입력값이 초기화되지 않는 문제를 수정했습니다.

한 줄 비우고 배경과 이유를 존댓말로 이어 쓴다. 여기서는 변경 내용을 반복하지 않는다.
- 버그 수정: 현재 재현되는 증상 (어느 화면에서, 어떤 조건에서, 무엇이 잘못 보이는지)
- 성능 개선: 현재 존재하는 성능 문제 (LCP, 번들 크기, 리렌더링 횟수 등 수치가 있으면 포함)
- 신규 기능: 기능을 추가하게 된 요구사항·목적
2~4문장.

### 변경 요약
커밋별 한 줄 표. 커밋 메시지를 그대로 옮기지 말고 무엇이 어떻게 바뀌었는지로 다시 쓴다.

```
| 커밋 | 변경 내용 | 파일 |
|------|-----------|------|
| `a1b2c3d` | 모달 닫힘 시 폼 상태 초기화 누락 수정 | `ProfileEditModal.tsx`, `useProfileForm.ts` |
```

- 파일 열은 경로를 빼고 파일명만 쓴다. 같은 이름의 파일이 여러 경로에 있으면 구분에 필요한 상위 디렉터리 하나만 붙인다.
- 파일이 5개를 넘으면 핵심 파일 3~4개만 쓰고 `외 N개`로 줄인다.
- 동일 목적의 fixup·typo 커밋은 한 행으로 합칠 수 있다. 합친 경우 파일도 합집합으로 쓴다.

### 변경 상세
선택 문단. 변경 요약만으로 리뷰어가 의도를 파악할 수 있으면 문단 자체를 생략한다.
노출 기준: 로직 분기 추가, 상태 관리·데이터 흐름 변경, API 호출 방식 변경, 이유가 코드에 드러나지 않는 선택.
커밋 단위가 아닌 기능 단위로 `### 소제목`과 존댓말 설명을 쓴다. 코드 블럭은 핵심 부분만 짧게.
길어지면 먼저 생략 기준을 다시 적용해 줄인다. 그래도 긴 코드 블럭이나 로그가 필요하면 GitHub가 렌더링하는 `<details><summary>제목</summary> ... </details>`로 접는다. `<summary>` 다음과 `</details>` 앞에 빈 줄을 두어야 안쪽 마크다운이 렌더링된다.

### 영향 범위
이번 변경이 영향을 주는 화면과 케이스를 항목으로 나열한다. diff의 호출 경로를 따라가 실제 노출 지점을 확인한다.
```
- 설정 페이지 프로필 편집 모달, 저장 후 다시 여는 케이스
- 모바일 Safari, 화면 너비 375px 이하에서 모달이 전체 화면으로 열리는 케이스
```
영향 없는 영역을 명시할 필요가 있으면 "영향 없음: ~" 한 줄로 덧붙인다.

### 스크린샷
선택 문단. 화면에 보이는 변화(레이아웃, 스타일, 문구, 노출 조건)가 있을 때만 쓰고, 없으면 문단 자체를 생략한다.
판단은 diff로 한다. 컴포넌트 마크업(JSX·템플릿), 스타일 파일, 문구 리소스가 바뀌었으면 화면 변동으로 본다. 로직만 바뀌었거나 결과 화면이 같은 리팩터링이면 생략한다.
- 같은 화면, 같은 조건의 Before/After를 표로 나란히 둔다. 신규 화면이면 After 열만 쓴다.
- 반응형 변경이면 뷰포트별로 행을 나눈다. 애니메이션·인터랙션은 GIF나 영상으로 첨부한다.
- 이미지는 GitHub 웹 편집기에 끌어다 놓아야 올라가므로 `{Before 이미지}` 같은 자리표시자로 남기고, 첨부가 필요하다고 사용자에게 알린다.

```
| Before | After |
|--------|-------|
| {Before 이미지} | {After 이미지} |
```

### 검증
리뷰어나 QA가 그대로 따라 할 수 있는 테스트 방법을 쓴다.
- 수동 검증: 사전 조건(계정 상태, API 응답, 브라우저·기기) + 진입 경로 + 기대 결과
  예) 로그인 상태로 `/settings` 진입 → 프로필 편집 모달에서 이름 변경 후 저장 → 모달을 다시 열면 빈 입력값 대신 저장된 이름 노출 확인
- 테스트 코드: 추가·수정한 테스트 파일명과 검증 내용
- 체크박스 없이 일반 항목(`- `)으로 나열한다.

### 참고
파악에 도움이 되는 링크만 3~5개 이내로.
- 이슈 티켓 URL. GitHub Issues면 머지 시 이슈가 닫히도록 `Closes #{번호}`로 쓴다(닫으면 안 되는 이슈는 `Refs #{번호}`)
- 관련 문서·기획서
- 선행 PR, 참조한 커밋
- 없으면 티켓 링크 한 줄만 남긴다. 티켓도 없으면 `관련 이슈 없음` 한 줄만 남긴다.

## 4. 출력 템플릿

````markdown
## 개요
{한 줄 요약: 어느 화면의 무엇을 어떻게 했습니다.}

{배경·이유}

## 변경 요약
| 커밋 | 변경 내용 | 파일 |
|------|-----------|------|
| `{hash}` | {변경 내용} | `{Component.tsx}`, `{useHook.ts}` |

## 변경 상세
### {기능 단위 소제목}
{설명}

## 영향 범위
- {화면}, {케이스}

## 스크린샷
| Before | After |
|--------|-------|
| {Before 이미지} | {After 이미지} |

## 검증
- {데이터 조건} + {진입 경로} → {기대 결과}
- `{Component.test.tsx}` : {검증 내용}

## 참고
- 티켓: {URL}
````

## 5. 반영

1. 완성본을 임시 `.md` 파일에 저장하고 `proofread-ai-slop` 스킬을 detect 모드로 한 번 실행한다.
   - `## ` 문단 구성과 순서, 변경 요약 표, 커밋 해시와 파일명, 검증 문단의 `→`(`arrow_per_100_sent`)는 이 템플릿의 요구사항이다. 지적되어도 `keep_reason`에 근거를 적고 유지한다.
   - verdict가 `CLEAN`이 아니면 리포트를 함께 보여 주고, 사용자가 승인한 항목만 fix 모드로 교정한다.
2. 완성본을 채팅에 마크다운 코드 블럭으로 출력한다.
3. 사용자가 반영을 요청하면 1에서 저장한 파일로 `gh pr edit {번호} --body-file {파일}`을 실행해 갱신한다. PR이 없으면 `gh pr create --base {target} --title "{제목}" --body-file {파일}`로 생성한다. 본문에 백틱과 줄바꿈이 많으므로 `--body` 인자로 직접 넘기지 않는다.
4. 사용자 확인 없이 PR을 생성·수정하지 않는다.
